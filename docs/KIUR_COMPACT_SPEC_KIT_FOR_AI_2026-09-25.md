**آخر حالة تنفيذ محلية:** راجع [تقرير تقدم 26 سبتمبر 2026](./KIUR_REMEDIATION_PROGRESS_2026-09-26.md) قبل اختيار بند للعمل؛ افحص الكود والاختبارات مجدداً لأن التقرير قد يتقادم.

## عقد العمل الثابت

1. طلب المستخدم الحالي أولاً، ثم `AGENTS.md` الأقرب إن وجد، ثم حالة المستودع الحالية، ثم هذه الوثيقة. افحص `git status --short` و`git rev-parse HEAD` قبل الاستنتاج. حافظ على تغييرات الآخرين ولا تنشر أو تعدل خدمة خارجية دون طلب صريح حالي.
2. KIUR منصة تعليم طبي عربية RTL للطلاب والأساتذة والإدارة والمالك. مصدر صلاحيات وجلسات ومحتوى التقييم هو الخادم وD1؛ لا تعتمد على إخفاء زر في المتصفح. تحقق من الأدوار والنطاق الأكاديمي وملكية السجل لكل مسار. لا تجعل نموذج ذكاء اصطناعي أو واجهة المستخدم مرجعاً للدرجات أو الأذونات.
3. ميّز في كل تقرير بين **حقيقة مؤكدة بالشيفرة** و**استنتاج/خطر مشروط** و**إعداد إنتاج غير مفحوص**. اذكر الملف والسطر أو الاختبار الذي يثبت كل ادعاء. لا تقل «آمن تماماً» أو «يعمل في الإنتاج» بناء على اختبار محلي.
4. تعامل مع تسجيل الدخول و2FA واستعادة الحساب والامتحانات والشراء والنشر والحذف كمسارات عالية الخطورة. ابدأ باختبار سلبي قبل التعديل: حساب آخر، دور آخر، جلسة ملغاة، رمز منتهي، طلب مكرر، سباق طلبين، ومدخل عدائي. لا تفتح ثغرة لتسهيل الواجهة.
5. نفذ أصغر تغيير متماسك في الملفات المعنية. استعمل بيانات حقيقية ومخزناً حقيقياً للمسار الإنتاجي؛ لا تضف fallback تجريبياً خفياً. اشرح الترحيل والعودة قبل تغيير قاعدة البيانات، واجعل الهجرات إضافية حيث أمكن.
6. اختبر العربية/RTL والهاتف وسطح المكتب والحالات: انتظار، نجاح، خطأ، انقطاع، فارغ، انتهاء جلسة. تحقق من لوحة المفاتيح وقارئ الشاشة، والروابط والنصوص الظاهرة.

## أولويات الإصلاح الحالية

`P0`: منع كشف أسرار المستخدم من API الإدارة؛ سياسة ربط Google/Firebase تحترم معرّف الموفر الثابت؛ حماية إعادة إعداد 2FA والجلسة الملغاة.

`P1`: إنهاء التسجيل بشاشة توثيق البريد؛ إصلاح زر Google بعد الإلغاء؛ توحيد مسار Google وإعداداته؛ دعوة الموظفين وتوثيقهم.
`P2`: إزالة واجهة اختيار Google المحلية المضللة والمعاينات في الإنتاج؛ رسائل أخطاء واستعادة واضحة؛ labels وروابط ونص كلمة المرور؛ إزالة inline handlers وتقوية CSP.

التفصيل والدليل ومعايير القبول لكل بند موجودة في وثيقة المتطلبات. إذا تغيّرت الشيفرة، أعد إثبات البند قبل التنفيذ ولا تنسخ أولويات قديمة آلياً.

## بروتوكول تنفيذ مقتصد للموديل

1. اختر بنداً واحداً، اقرأ 2–5 ملفات لازمة فقط، واكتب ملخصاً من سطرين: السلوك الحالي، السلوك المطلوب، وخطر الرجوع.
2. اكتب اختباراً ذا معنى للحالة السلبية عالية الخطورة، ثم نفذ التغيير، ثم تحقق من المسار الإيجابي والسلبي. لا تكثر اختبارات تكرر تفاصيل التنفيذ.
3. شغّل `npm run typecheck` والاختبارات المركزة باستخدام `TEST_TARGET=src` حيث يناسب، ثم البناء الجاف `npm run build` عند تغيير Worker أو الأصول. إذا تعطل مشغل الاختبارات بسبب البيئة، اذكر العطل حرفياً ولا تدّع النجاح. شغّل المجموعة الكاملة قبل قرار الإطلاق.
4. سلّم في كل خطوة: الملفات المتغيرة، لماذا، نتائج التحقق بالأرقام، الأخطار الباقية، وإعدادات Console أو الأسرار التي تحتاج تحققاً خارج الشيفرة. توقف عند مسألة صلاحيات أو هوية ملتبسة واطلب قراراً محدداً، ولا تخمّن سياسة ربط الحسابات أو دور المالك.

## تعريف الاكتمال

لا يُغلق بند حتى تنجح معايير قبوله، ويُراجع سلوك الهاتف وسطح المكتب عندما يغيّر واجهة المستخدم، وتبقى بيانات الحساب والامتحان والشراء محمية بالخادم. لا يعني اكتمال الشيفرة اكتمال إعداد Google/Firebase/Cloudflare أو إذن النشر.
